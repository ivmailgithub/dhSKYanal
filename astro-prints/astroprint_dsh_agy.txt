  ### Why the Previous Print Looked Like "Abstract Art"

  Inspecting the previous workspace logs and files (astroprint_dsh_agy.txt, orig_view.png, and convert.js) reveals
  four specific reasons why the lithophane print became an unreadable texture:
  1. Severe Image Resolution Bottleneck:
  The input image used was a 472 × 750 px JPEG thumbnail. For a 130 mm diameter cylinder (circumference C = π × 130 ≈
  408.4 mm), 750 pixels across the circumference is only ~1.8 pixels/mm (~46 DPI). Individual constellation labels
  like "Orion" were only 10 pixels wide—turning text and small stars into blurry pixelated smudges.
  2. Extreme Mesh Decimation:
  In convert.js, the angular resolution was set to --angle 180. Spreading 180 points over a 408.4 mm circumference
  meant each polygon facet was 2.27 mm wide. Any star, line, or letter smaller than 2.3 mm was decimated before the
  slicer even saw it.
  3. Photographic Stippling vs. Lithophane Physics:
  The vintage map had stippled Milky Way shading, soft gradient glows, and small serif fonts. Lithophanes encode
  pixel brightness into wall thickness (e.g. 0.8 mm to 2.2 mm). Stipples and low-contrast gradients translate into
  random rough surface ripples that look like melted candle wax or rough stone rather than stars.
  4. FDM Nozzle Physical Constraints:
  A standard 0.4 mm nozzle cannot resolve fine 0.1 mm star chart lines. Lines must be at least 0.6–0.8 mm wide (2
  perimeters) and star dots at least 1.0–3.0 mm diameter to stay continuous and legible.
  5. Radius Parameter Typo:
  In the run log, the command passed --radious 130 (with an extra o). Because of the typo, the script silently
  ignored it and defaulted to a radius of 35.0 mm instead of 65.0 mm.

  ### Root Cause of the OOM Crash

  At a resolution of 720 angular steps × 500 axial steps (360,000 cells):
  1. In-Memory Line Buffering: convert.js was appending all generated STEP entities to an in-memory array (this.
  lines.push(...)). Across all four assembly components (Space_Background, Stars, Constellation_Lines, Index_Lines),
  this generated over 35 million STEP entity strings. Keeping all 35M strings in the V8 heap exceeded Node's ~4.14 GB
  default memory ceiling during Constellation_Lines.
  2. Object & String Allocations: Point lookup dictionaries (bgOutPts, bgInPts, outPts, inPts) used composite string
  keys ("${i},${j}"), creating over 1.4 million dictionary entries and temporary string objects.
  3. Array Conversions: Shell assemblies were created with .map(f => '#' + f).join(','), creating multi-million
  element string arrays and a ~15 MB string allocation for each shell.
  ──────
  ### Key Optimizations Implemented
  In convert.js:
  • Direct Buffered File Streaming: Implemented BufferedWriter with a 4 MB buffer using fs.writeSync. STEP statements
  and headers are written directly to disk as they are generated rather than accumulated in memory.
  • Typed Array Point & Face Buffers: Replaced {} objects with contiguous Int32Array buffers indexed by (j * NW + i)
  and Float32Array / Float64Array buffers for grid radii and trigonometric lookups (cosTh, sinTh, zVals).
  • Chunked Shell Writing: Replaced faces.map(...).join(...) with emitShell(), streaming face references in 32 KB
  string chunks directly into the write buffer.
  • Fast Scalar Triangle Generation: Added makeTriFast() to compute plane normals and placements directly with scalar
  math, eliminating millions of intermediate [x, y, z] arrays.

  Heap memory usage dropped from >4.2 GB down to <70 MB.
